## 1. 部署前你需要知道什么

### 1.1 你会得到什么

| 组件 | 作用 | 谁可以访问 |
|------|------|------------|
| **Worker A** | 发帖、登录、关注、Token 签发 | 仅本人 Web（CORS 白名单） |
| **Worker B** | 读帖、图片、粉丝 Token 校验 | 公网（粉丝 / 其它节点） |
| **Web（Pages）** | 站主私人首页（Timeline、发帖、设置） | **仅站主本人**（整站登录门禁，类 X 私人账号） |

### 1.2 与注册中心的关系

- 节点默认连 **公共注册中心 API**：`https://hailuo-registry.allovo.eu.org`（**不是**管理后台 `admin.*` 域名）。
- **信任锚（M9-PH-TA）**：节点源码钉死官方主中心公钥；仅改 `REGISTRY_URL` 不够——须过 well-known 验签。Fork 自建联邦须换锚，见 [`deploy.md` §主中心信任锚](./deploy.md#主中心信任锚m9-ph-ta--开源后必读)。
- 首次部署**不必**立刻完成注册；先让 A/B/Web `/health` 与发帖跑通，再完成注册中心登记。
- **官方公告同步依赖注册中心鉴权**：Worker A 会定时请求注册中心 `GET /api/posts/feed` 拉取官方公告。这个接口需要节点凭证（注册后写入 D1 的 `node_api_token` / `owner_user_id`），并要求 Worker A 用本节点 `ED25519_PRIVATE_KEY` 对请求签名；注册中心用登记时保存的节点公钥验签。
- **官方公告同步是低频任务**：节点 cron 仍每 5 分钟处理关注节点聚合，但注册中心官方公告默认约 **1 小时**检查一次，并按节点身份稳定错峰，避免大规模部署后所有节点同时打注册中心。
- **官方公告展示位置**：官方公告会写入关注 Feed，同时 Worker B 的 `/posts` 会只读合并注册中心来源的公告，所以 Web 的「关注」和「推荐」都会显示。
- **官方公告可手动同步**：登录 Web 后进入 **设置 → 运行日志**，点击「拉取官方公告」可立即尝试同步；为保护注册中心，手动拉取按 UTC 日期限制每天 3 次，失败也计入尝试次数。
- **立即同步 daily-sync 按钮**（设置 → 注册中心对接 → 「立即同步」）：**成功后 24h 用户层冷却**（前后端双层；独立 D1 键 `registry_daily_sync_last_manual_at`，与 cron `last_success_at` 隔离）。命中冷却 → 429 `MANUAL_DAILY_SYNC_COOLDOWN`。`force=true` 仍跳过 cron 的 `interval × 12h` 节流。窗口可用 secret/env `MANUAL_DAILY_SYNC_COOLDOWN_HOURS` 覆盖（缺省 24）。失败不占冷却。详见 `docs/m16-daily-sync-cooldown-plan.md` v0.2。
- **更换注册中心通行证**（设置 → 注册中心对接 → 「更换注册中心通行证」）：**无 quota / 无 cooldown / 无 limit**——点击立即代理 `POST /api/node/rotate-token` 并原子落盘 AES-GCM 密文。失败可重试。v0.6 计划评估是否加 N 次/天节流，详见 `docs/m16-daily-sync-cooldown-plan.md` §4 待决策 #2。
- **刷新列表 / 自测公开 /health / 联邦解析**：**只读 Worker B 公开接口**——不调注册中心、不写 D1——**无限流需要**。
- 节点侧**不再需要配置 `HMAC_SECRET`**。这避免成千上万个自部署节点共享同一密钥，也避免你本地随机生成的密钥和注册中心不一致导致官方公告拉取失败。

### 1.3 硬约束（安全 · 配额）

- **Worker A 不要绑公网 Custom Domain**；粉丝只访问 Worker B。
- **升级 redeploy 不会删除 D1 数据**；Migration 只加表/列，脚本不删库。
- **Free Tier 优先**：仓库默认不把 R2 写死进配置。一键部署会尝试建海螺媒体桶；建不成时图片仍走 KV。详见 [§9「不要删海螺媒体桶」](#q不要删控制台里的-hailuo-node-media--吗)。
- **节点 Cloudflare 账号 ≠ 注册中心账号（必须分开）**：本节点已占用约 7/10 个免费 D1 库；官方注册中心另需多个 D1。两者放进同一账号会立刻超过 Free 上限。站主只需连公共注册中心 API，**不要**在本账号再部署官方 `hailuo-registry`。细则见 [`deploy.md` 硬约束](./deploy.md#硬约束部署前必读--r-audit-sep-a2)。

### 1.4 多租户 URL 设计（A/B/Pages 各自独立 ID）

每位站主在**自己的 Cloudflare 账号**下部署；**Worker A、Worker B、Web Pages 各用独立 32 位 hex**（`WORKER_A_RESOURCE_ID` / `WORKER_B_RESOURCE_ID` / `PAGES_RESOURCE_ID`）。公开资源名使用同一个 6 位 `DEPLOY_GROUP_CODE` 加各自 32 位 ID 的前 28 位，既能看出同属一个海螺节点，也避开 Cloudflare Worker previews 的 54 字符脚本名限制。同一账号 + 槽位（`HAILUO_NODE_SLOT`，默认 1）下，组码与资源 ID 由账号哈希稳定派生，重复部署复用同名资源；换账号或槽位才会换一组名字。账号 `workers.dev` 子域由 Cloudflare 控制台显示（如 `<your-subdomain>`），脚本**不会**强行改成 UUID：

| 组件 | 项目名（wrangler `name`） | 公网 URL 形态 |
|------|---------------------------|---------------|
| Worker A | `hailuo-worker-a-{group}-{shortA}` | `https://hailuo-worker-a-{group}-{shortA}.{账号子域}.workers.dev` |
| Worker B | `hailuo-worker-b-{group}-{shortB}` | `https://hailuo-worker-b-{group}-{shortB}.{账号子域}.workers.dev` |
| Web Pages | `hailuo-web-{group}-{shortP}` | `https://hailuo-web-{group}-{shortP}.pages.dev` |

示例（账号子域用 `<your-subdomain>` 占位，`c079ca` 为同组码，后缀仅作形态示意）：

- Worker A：`https://hailuo-worker-a-c079ca-a1b2c3d4e5f6478990abcdef1234.<your-subdomain>.workers.dev`
- Worker B：`https://hailuo-worker-b-c079ca-fedcba0987654321a1b2c3d4.<your-subdomain>.workers.dev`

说明：

- Cloudflare 标准格式为 `{worker-name}.{account-subdomain}.workers.dev`（注意是 **`.workers.dev`**）。
- `finalize-hailuo-deploy.mjs` 会读取账号真实子域并写回 token / wrangler；Pages 只注入 **Worker B 的 `PUBLIC_WORKER_B_URL`**，登录/发帖再由 Worker B 经 Service Binding 转发到私密 Worker A。
- Worker A 的 `*.workers.dev` 仅写入部署卡片 / token / Pages 构建变量，**不写入公开文档、不交给粉丝**（见 §9）。
- **旧版单 UUID**：若 token 里已有 `DEPLOY_RESOURCE_ID` 且 `WORKER_A_NAME` 等已填，bootstrap **不会**覆盖；仅全新生成时三者 ID 独立。

## 2.1 路径 A：本地部署要准备什么

1. **本机已 clone/解压** 海螺节点仓库（例如 `E:\project\hailuo`）
2. **Node.js 18+**（脚本里会 `npm ci`）
3. **Cloudflare 账号** + 创建一个 **API Token**（权限：Workers Scripts、D1、Workers KV、Pages 编辑）
4. **通常只填 2 项**（其余由 M8-8 脚本自动生成）：

```powershell
cd E:\project\hailuo
Copy-Item scripts\cloudflare-api-token.example.json scripts\cloudflare-api-token.json
notepad scripts\cloudflare-api-token.json
```

| 字段 | 你要填什么 |
|------|------------|
| `CLOUDFLARE_ACCOUNT_ID` | 控制台 Account ID |
| `CLOUDFLARE_API_TOKEN` | API Token |

**自动生成（勿手抄）**：`JWT_SECRET`、`Ed25519` 密钥对、`INTERNAL_FORWARD_SECRET`、**部署占位 handle**（`BOOTSTRAP_HANDLE` = `hailuo_` + 10 位）、首次登录凭证（固定 `admin` / `admin`，登录后强制修改）、Worker A/B/Pages URL 写回 token 与 wrangler。

| 概念 | 示例 | 用途 |
|------|------|------|
| **部署占位 handle**（`BOOTSTRAP_HANDLE`） | `hailuo_a3k9mx2p7q` | wrangler 变量；未登记前的默认 `@handle`；**登记注册中心后以 D1 `users.handle` 为准** |
| **站主登录名**（`OWNER_LOGIN_USERNAME`） | `admin` | Web **整站登录页**（打开站点即需用户名+密码；首次登录后修改） |

5. **一键部署**：

```powershell
.\scripts\deploy-all.ps1
```

流程：Bootstrap → 部署 A/B → **M8-11 收尾**（解析 URL、Redeploy A、私有化 A）→ 构建并部署 Pages → 尽力自动拉取一次官方公告 → 控制台打印 **`scripts/deploy-login-card.txt`**（只含登录名/密码、Web 与 Worker B 公开地址）。

6. **部署完成后**：打开卡片上的 Web 站点 → **登录页直接输入** `admin` / `admin`（API 入口已由 `PUBLIC_WORKER_B_URL` 自动注入）→ 登录后会自动跳转 **设置** 修改用户名与密码。

> **登录技术说明（M2-1b-9）**：浏览器会先请求 Worker B `GET /auth/login-params`，再由 Worker B 内部转发到 Worker A 获取 salt，在本地完成 PBKDF2 后只上传 `password_hash`（不传明文密码）；Worker 边缘不做 PBKDF2，避免 Free Tier 10ms CPU 上限。登录按钮可能等待约 0.1–0.5 秒属正常。

可选验证：

```powershell
npm run smoke:remote
```

## 3. 三步部署（路径 B：GitHub Deploy 按钮）

> **顺序不可颠倒**：A（含 D1）→ B（Binding 指向 A）→ Pages（需要 B 的 URL）。

**Canonical Deploy URL**（也可从 README 点按钮）：

| 步骤 | URL |
|------|-----|
| Worker A | `https://deploy.workers.cloudflare.com/?url=https://github.com/tsjworldcode/hailuo-node-cf&subdir=apps/worker-a` |
| Worker B | `https://deploy.workers.cloudflare.com/?url=https://github.com/tsjworldcode/hailuo-node-cf&subdir=apps/worker-b` |

向导里 **Install / Build / Deploy** 应预填为根目录 `npm ci` + 对应 workspace 脚本；若为空请手动填（见 [`deploy.md` §Deploy 按钮](./deploy.md#deploy-按钮与-cloudflarebindingsm8-5)）。

### 步骤 1：Deploy Worker A（写层 + 数据库）

点击下面按钮，登录 Cloudflare + GitHub，按向导填写 Secret/变量（字段说明来自 `apps/worker-a/package.json` 的 `cloudflare.bindings`，见 [§6](#6-配置分层首次必填-vs-以后再补)）：

[![Deploy Worker A to Cloudflare](https://deploy.workers.cloudflare.com/button)](https://deploy.workers.cloudflare.com/?url=https://github.com/tsjworldcode/hailuo-node-cf&subdir=apps/worker-a)

**向导逐步（首次）**：

1. 授权 GitHub → Cloudflare 在**你的账号**下 fork 完整 `hailuo` 仓库（含 `packages/`、`web/`）。
2. 确认 **Root directory = 仓库根**（不要只选 `apps/worker-a`）。
3. 核对构建命令：`npm ci` → `npm run build:worker-a` → `npm run deploy:worker-a`。
4. 按提示填写 Secret：`JWT_SECRET`、`ED25519_PRIVATE_KEY`、`INTERNAL_FORWARD_SECRET`（后两项见 §2 `keys:generate`）。
5. 填写变量：`BOOTSTRAP_HANDLE`；`WORKER_B_URL` / `WORKER_A_ORIGIN` 可先用占位，§4 再改。
6. 点击 Deploy；Cloudflare 自动创建 D1/KV 并执行 **migration**（binding 名 `DB`）。
7. 成功后面板显示 Worker 名 **`hailuo-worker-a-{group}-{shortA}`**（同组码和短 ID 由脚本生成，与 B/Pages 后缀独立）。

**完成后记下**：Worker A 无需对外宣传 `*.workers.dev` 地址。

---

### 步骤 2：Deploy Worker B（读层）

**必须先完成步骤 1。**

[![Deploy Worker B to Cloudflare](https://deploy.workers.cloudflare.com/button)](https://deploy.workers.cloudflare.com/?url=https://github.com/tsjworldcode/hailuo-node-cf&subdir=apps/worker-b)

**向导逐步**：

1. 同样 fork / 选你已 fork 的仓库；Root = 仓库根。
2. Build/Deploy：`npm run build:worker-b` / `npm run deploy:worker-b`。
3. Secret：`INTERNAL_FORWARD_SECRET` 与 Worker A **完全相同**。
4. 变量：`BOOTSTRAP_HANDLE`、`ED25519_PUBLIC_KEY` 与 A 一致；`FOLLOWER_TOKEN_MODE` 保持 `public-read`。
5. **Service Binding** `WORKER_A` → `hailuo-worker-a-{group}-{shortA}`（与 A 的 Worker 名一致；bootstrap 会按 token 回填 wrangler）。

**完成后记下 Worker B 的 https 地址**（对外入口），例如：

`https://hailuo-worker-b.<你的子域>.workers.dev`

---

### 步骤 3：Web 前端（Cloudflare Pages）

Deploy 按钮**暂不支持 Pages**；在 Dashboard 手动 **Connect to Git**：

1. **Workers & Pages** → **Create application** → **Pages** → **Connect to Git**。
2. 选你 fork 的 **`hailuo`** 仓库，授权读权限。
3. **Set up builds and deployments**：

| 字段 | 填写值 | 常见误填 |
|------|--------|----------|
| Production branch | `main` | — |
| Framework preset | **None** | 勿选 Astro 自动模板（会改路径） |
| Root directory | **留空或 `/`** | ❌ 不要只填 `web/` |
| Build command | `npm ci && npm run build --workspace=web` | ❌ 不要在 `web/` 里单独 `npm install` |
| Build output directory | `web/dist` | ❌ 不是 `dist` |

4. **Environment variables** → **Production** → Add variable：

| 变量 | 值 |
|------|-----|
| `PUBLIC_WORKER_B_URL` | 步骤 2 的 Worker B https 地址（**无尾斜杠**） |
| `PUBLIC_WORKER_B_URL` | 步骤 2 的 Worker B https 地址（**无尾斜杠**；Web 唯一 API 入口） |

5. **Save and Deploy**，等待构建绿勾。
6. 记下 Pages 默认域名，例如 `https://hailuo-web.pages.dev`（项目名可自定）。
7. 回到 §4 把 `WORKER_A_ORIGIN`、Pages 变量与 Worker 变量对齐后 **Redeploy A/B**。

**构建失败排查**：

- `Cannot find module '@hailuo/...'` → Root 必须是仓库根，构建命令含 `npm ci`。
- Timeline 空白但构建成功 → 检查 `PUBLIC_WORKER_B_URL` 是否 Production 环境、是否漏填。
- 登录页提示「站点未配置节点地址」→ 检查 `PUBLIC_WORKER_B_URL` 是否已设并重新部署 Pages。

本地 Web 变量样板：`web/.env.example` → `.env.local`。

## 4. 部署后回填变量

在 Cloudflare 控制台 → 对应 Worker → **Settings → Variables** 更新（或用 `wrangler`）：

| Worker | 变量 | 填什么 |
|--------|------|--------|
| **A** | `WORKER_B_URL` | 步骤 2 的 B 地址 |
| **A** | `WORKER_A_ORIGIN` | 步骤 3 的 Pages 地址（CORS，F-15） |
| **A** | `BOOTSTRAP_HANDLE` | 你的 handle |
| **A** | `ED25519_PUBLIC_KEY` | `npm run keys:generate` 的公钥 |
| **B** | `BOOTSTRAP_HANDLE` / `ED25519_PUBLIC_KEY` | 与 A 相同 |

改完后对 A、B 各 **Redeploy 一次**（或 Dashboard → Deployments → Retry）。

## 5. 日常升级（不毁数据）

Fork 仓库 `git pull` 上游更新后，**命令与首次相同**：

```powershell
cd hailuo
npm ci
npm run deploy:all          # A（migrate:production + deploy）→ B
# Pages：git push 后 Cloudflare 自动构建，或 Dashboard 手动 Retry
```

**承诺**：

- 不会删除你的 D1 / KV
- Migration 已执行过的版本会跳过
- Secret 存在 Cloudflare，不会因代码 deploy 丢失

**升级后怎么验**：见 [`升级验证.md`](./升级验证.md)（`npm run smoke:remote` + 可选 D1 行数对比）。维护者本地模拟：`npm run verify:upgrade:local`。

## 6. 配置分层：首次必填 vs 以后再补

### 6.1 Deploy 向导 / 首次建议填写

| 名称 | 类型 | 说明 |
|------|------|------|
| `BOOTSTRAP_HANDLE` | 变量 | 部署占位 handle（≠ 登录名；登记后以 D1 为准） |
| `JWT_SECRET` | Secret | 站主登录 Web |
| `ED25519_PRIVATE_KEY` | Secret | 粉丝 Token 签发 |
| `ED25519_PUBLIC_KEY` | 变量 | 与私钥配对 |
| `INTERNAL_FORWARD_SECRET` | Secret | **A 与 B 必须相同** |
| `REGISTRY_URL` | 变量 | 默认已设 `https://hailuo-registry.allovo.eu.org` |

### 6.2 部署后再补（不阻塞首次）

| 名称 | 何时 |
|------|------|
| `WORKER_B_URL` | B 部署完成后 |
| `WORKER_A_ORIGIN` | Pages 域名确定后 |
| `PUBLIC_WORKER_B_URL` | Pages 构建环境变量 |
| `PUBLIC_WORKER_B_URL` | Pages 构建环境变量（Worker B 公开入口，Web 唯一 API 入口） |
| `FOLLOWER_TOKEN_MODE=enforced` | Web 能稳定拿粉丝 Token 后 |

### 6.3 节点签名与官方公告同步

注册中心官方公告不是从管理后台域名拉取，而是从公共 API 域名 `https://hailuo-registry.allovo.eu.org/api/posts/feed` 拉取。注册中心代码里的鉴权顺序是：

1. `nodeReadAuthRequired`：校验节点请求头 `X-Hailuo-Node-User-Id` 和 `Authorization: Bearer <node_api_token>`，定位到注册中心里的节点记录。
2. `requireNodeSignature`：用该节点 `users.pubkey` 校验 `X-Timestamp` / `X-Nonce` / `X-Signature`，防篡改与防重放。
3. 速率限制与 feed 查询。

所以生产环境要同时满足两类配置：

| 配置 | 存在哪里 | 来源 |
|------|----------|------|
| `node_api_token` / `owner_user_id` | 你的 Worker A D1 `system_config` | 完成注册中心登记后写入 |
| `ED25519_PRIVATE_KEY` | 你的 Worker A Wrangler Secret | 部署脚本生成；必须与注册中心登记的公钥配对 |
| `users.pubkey` | 注册中心 D1 | 新注册自动写入；老节点由注册中心 migration `0021_user_pubkey.sql` 从成功 challenge 回填 |

已经注册过的节点一般**不需要重新注册**：注册中心部署并执行 `0021_user_pubkey.sql` 后，会从历史成功 challenge 回填公钥；节点只要保留原来的 `ED25519_PRIVATE_KEY` 并重新部署 Worker A，就能继续拉取官方公告。

升级到包含“运行日志”的版本后，还需要确保远程 D1 已执行最新 migration：

```powershell
npm exec -- wrangler d1 migrations apply IDENTITY_DB --remote --env production --config apps/worker-a/wrangler.toml
npm exec -- wrangler d1 migrations apply GOVERNANCE_DB --remote --env production --config apps/worker-a/wrangler.toml
npm exec -- wrangler d1 migrations apply CONTENT_DB --remote --env production --config apps/worker-a/wrangler.toml
```

登录 Web 后进入 **设置 → 运行日志**，可以查看“节点凭证是否已配置”“节点签名是否已配置”“官方公告上次拉取错误”。这里也提供「拉取官方公告」按钮，供站主手动触发一次同步；每天最多 3 次，失败也计数，避免反复点击给注册中心造成压力。

自动同步的计时从节点 D1 `system_config.registry_official_feed_last_checked_at` 开始算；首次部署或该值缺失/非法时，下一次 5 分钟 cron 分支（`minute % 5 === 0`）会直接尝试拉取。`deploy-all.ps1` 在部署成功后也会通过 Worker B 站主代理尽力拉取一次官方公告；若此时节点尚未完成注册、当天手动额度已用完，或网络暂不可用，会只打印 `SKIP` 并继续完成部署。每次自动或手动拉取成功/失败后都会更新这个时间，因此它不是单纯从部署时刻开始计时。

若运行日志显示“注册中心官方公告拉取完成：0 条”，先检查注册中心生产 D1 中是否真的存在可公开拉取的公告。公开 feed 只返回 `status='published'` 且 `published_at IS NOT NULL` 的行；后台里仍是草稿、已归档，或写到了另一个 Cloudflare/D1 环境，节点都会拉到 0 条。注册中心维护者可在 `hailuo-registry` 仓库执行只读检查：

```powershell
npm exec -- wrangler d1 execute DB --remote --config workers/registry-gateway/wrangler.toml --command "SELECT status, COUNT(*) AS c FROM official_posts GROUP BY status;"
npm exec -- wrangler d1 execute DB --remote --config workers/registry-gateway/wrangler.toml --command "SELECT post_id, title, status, published_at, updated_at FROM official_posts ORDER BY updated_at DESC LIMIT 20;"
```

## 9. 常见问题

### Q：Deploy 按钮和 fork 整仓是什么关系？

按钮会 fork **完整 monorepo** 到你 GitHub；`subdir=apps/worker-a` 只指定**哪个 Worker 入口**部署，依赖仍在仓库根 `npm ci` 安装。

### Q：每次升级会删帖子吗？

**不会。** 只替换 Worker 代码；D1 独立存储；Migration 只增不改。升级也不会删 `hailuo-node-media-*` 桶。

### Q：不要删控制台里的 `hailuo-node-media-*` 吗？

**不要删。** 一键部署能开 R2 时，会建一个名字像 `hailuo-node-media-8226e6` 的桶（后 6 位是本组码，不是你的真名），并绑到 `HAILUO_IMAGE_R2`。这是海螺的媒体库：大图、视频、压缩包放这里；普通小图仍在 KV（`image-kv`）。

| 你看到的 | 做什么 |
|---|---|
| 小图（大约 10 MB 以内） | 优先放 KV |
| 更大的图，或不是图片的文件 | 有这个桶就放 R2 |
| KV 快满（大约 90%） | 之后的新文件改放 R2；旧图不自动搬走 |
| R2 快满（大约 90%） | 自动清掉可回收的旧对象，清到大约 70%；还挂在帖子上的不删 |

设置页「媒体存储」能看到是否已绑上，也能改这几档水位，保存后马上生效，不用重新部署。删掉这个桶或绑定后，已经放进去的大文件会读不出来，而且**不能**靠再部署把文件找回来。技术细节见 [`deploy.md` §2.2](./deploy.md#22-可选图片对象库m8-14--命名防误删--分流)。

### Q：删掉 Cloudflare 上的 Pages / Worker A / Worker B 再部署，D1 和 KV 会重建吗？

**通常不会。** `bootstrap-hailuo-cloudflare.ps1` 按**固定名称**查找已有资源并复用：

| 资源 | 查找方式 | 删 Worker/Pages 后 |
|------|----------|-------------------|
| **D1** | 数据库名 `node-db` | 只要 D1 没删，**复用同一库**（帖子/用户/登录凭证都在） |
| **KV** | 命名空间标题 `hailuo-node-posts-cache` 等 3 个 | 只要 KV 没删，**复用同一 id** |
| **Worker / Pages** | `hailuo-worker-a-{group}-{shortA}` / `hailuo-worker-b-{group}-{shortB}`；Pages 为 `hailuo-web-{group}-{shortP}`（同组码相同，短 ID 不同） | 删除后 redeploy 会按 token 中名称**重建**；URL 还包含账号 `workers.dev` 子域 |

注意：

- 只删 Worker A/B 和 Pages、**不删 D1/KV** → 再跑 `deploy-all.ps1` 会接回原来的 D1/KV（`wrangler.toml` 里已有 `database_id` / KV `id` 时优先用本地配置）。
- **若手动删除了 D1 或 KV** → bootstrap 会**新建**空库/空命名空间，旧数据无法自动恢复。
- token 里已填 `WORKER_A_NAME` / `WORKER_B_NAME` / `PAGES_PROJECT_NAME` 时，**项目名保持不变**；仅清空这三项（及可选的资源 ID 字段）才会重新生成新 ID。
- **旧版 `hailuo-node-worker-*` / `hailuo-node-web-*` 或共用 `DEPLOY_RESOURCE_ID`**：再跑 `deploy-all.ps1` 时 bootstrap 会**自动升级**为 `hailuo-worker-a|b|web` 三独立 UUID，并在 Cloudflare **新建**对应 Worker/Pages（D1/KV 仍接 wrangler 里已有 id）；验证通过后可手动删除旧的 `hailuo-node-*` 资源。

### Q：换域（新公开 HTTPS 地址）后还要改哪些部署变量？

**默认不用改、也不用 redeploy（M7-30g）。** Settings → **节点换域** confirm 成功后，注册中心、节点 D1 与 STATE_KV canonical 已更新；运行时公开基址以 D1 / KV 为准。`WORKER_B_URL` / `PUBLIC_WORKER_B_URL` **仅 bootstrap**，过时不更新也可。**wrangler / Pages 不会自动改**——也不再需要为换域去改它们。

例外（一次性，不是每次换域）：

1. Pages Functions **尚未**绑定 `STATE_KV`（与 Worker A/B 同 namespace id）→ 补绑一次（`finalize` 或控制台），之后换域免 redeploy Web  
2. 下次整仓升级时可选把 wrangler / token 里的 bootstrap URL 对齐新址  

完整 Checklist、自定义域注意、冒烟命令见 [`deploy.md` §节点换域部署清单（M7-30c）](./deploy.md#节点换域部署清单-m7-30c)。

**关注列表与 lookup 缓存**见 [`m7-30d-url-change-follows-cache.md`](./m7-30d-url-change-follows-cache.md)。**粉丝 Token、互证、私信**见 [`m7-30e-url-change-owner-faq.md`](./m7-30e-url-change-owner-faq.md)。

### Q：节点搬家（换 Cloudflare 账号 / 换主 D1）怎么做？

**用正规路径，不要默认原地覆盖。**

1. Settings → **节点搬家**：口令 **加密导出**（`hailuo-node-export-v2-enc`）  
2. 目标侧创建 `hailuo-node-db-{同组码}-import`，绑定 `DB_IMPORT`，跑 migrations  
3. Settings **导入**到 staging → 等对账 `import_ready=true`  
4. 本机跑 `scripts/cutover-db-import.ps1`（确认短语 `CUTOVER`）→ **手工** deploy Worker A → smoke  
5. 切流后 **重开站主 TOTP**；图片二进制与私信/群聊 **不在**本包内（私信用 M10-5b）

Web **不会**替你改 Cloudflare binding。完整步骤与逃生口说明见 [`deploy.md` §节点搬家正规路径（M9-7）](./deploy.md#节点搬家正规路径-m9-7)；计划 SSOT [`m9-7-staging-aes-gcm-plan.md`](./m9-7-staging-aes-gcm-plan.md)。

### Q：Worker A 的 `*.workers.dev` 地址要给别人吗？

**不要。** Worker A 默认应关闭公网 workers.dev；Web 只绑定 Worker B（`PUBLIC_WORKER_B_URL`），对外只宣传 Worker B / Pages。

### Q：注册中心 admin 页面和 REGISTRY_URL 一样吗？

**不一样。** 节点只连 API 根 `https://hailuo-registry.allovo.eu.org`；管理员后台是 `admin.hailuo-registry.allovo.eu.org`。

### Q：preview 环境要不要建？

**站主不需要。** 本指南仅 **production 一套**；preview 留给仓库维护者 CI。

### Q：Deploy 失败在 shared 包找不到？

在**仓库根**执行 `npm ci`，不要只在 `apps/worker-a` 里 `npm install`。见 `npm run test:m8-4`。

### Q：注册中心信任锚是什么？改 `REGISTRY_URL` 够不够？

**不够。** 开源节点钉死官方主中心（`reg1`）公钥：冷启动 / 改 `REGISTRY_URL` 时必须通过 `/.well-known/hailuo-registry-identity` 锚点验签，否则拒绝登记落库。跟随官方联邦时**不要**改源码里的信任锚常量。

- 备用注册中心不能靠 env 裸写 URL；须等官方主中心下发已签名的 `add_registry`。  
- **Fork 自建联邦**：须整体替换 `apps/worker-a/src/lib/primaryRegistryTrustAnchor.ts` 中的公钥与默认 URL，再指向自建主中心。详见 [`deploy.md` §主中心信任锚](./deploy.md#主中心信任锚m9-ph-ta--开源后必读) 与 [`m9-ph-trust-anchor-plan.md`](./m9-ph-trust-anchor-plan.md)。
